# Assessment methods, provenance and execution

There are four supported assessment methods and three evidence families. A run does not necessarily execute all four. Report `method_catalog` and `methods_enabled` identify the selected methods; `timing.stages` identifies the stages actually run. A selected stage can be skipped after baseline rejection or a recovery failure.

| Method | Implemented by | Purpose | Evidence family | Default |
| --- | --- | --- | --- | --- |
| 1. Remote PHP/version assessment | php_version.py | Identify advertised versions and compare fix thresholds | Advertised runtime version | Enabled |
| 2. ProjectDiscovery method in Python | template_method.py | Multipart control/probe comparison, template memory-error matcher and local version fallback | Multipart/OOM behavior | Enabled when --active is selected |
| 3. Assetnote active scanner | Unchanged vendored scanner through adapter | Upstream control/probe, response differences and version fallback | Multipart/OOM behavior | Optional |
| 4. Trusted runtime/package evidence | scanner.py attestation verifier | Assess signed assertions from a trusted collector about packages, CVEs and active workers | Authenticated runtime inventory | Optional; requires backend collector |

PHP fingerprints such as PHPSESSID are discovery hints within method 1. Endpoint selection, scope validation, recovery checks, result fusion and report generation are workflow stages, not additional vulnerability detectors. Six reviewed repositories do not equal six scanning methods. Both active engines share underlying techniques and are not independent evidence votes.

## ProjectDiscovery attribution and adaptation

Source: https://github.com/projectdiscovery/nuclei-templates/blob/main/http/cves/2026/CVE-2026-109618.yaml

Reviewed source git blob: `9d89d77dbd5f269dd0039534f204c16389911f46`.

Authors credited in the template: lcfr_hax, assetnote, princechaddha, s4e-io. MIT copyright and full license retained in vendor/PROJECTDISCOVERY-LICENSE.txt. The exact fetched source is included as vendor/CVE-2026-109618.reference.yaml for review, not execution. The YAML's Nuclei digest does not sign the Python adaptation.

The Python implementation adapts:

- The minimal multipart control request.
- The three probe profiles and original LF multipart body builder.
- The memory-exhaustion response-text matcher.
- Rejection handling and early stopping on an observed fix-level version.
- Version fallback after behavioral assessment.

Documented changes from the template:

1. Uses standard-library HTTP rather than Nuclei. Nuclei is not installed, imported or executed.
2. Preserves the selected endpoint path. The source raw requests target `/`.
3. Omits the redundant final GET used to emit a version-only Nuclei finding. Version fallback is computed locally instead. Maximum native requests are one control plus three probes.
4. Requires a successful 2xx control. Stops on redirects and rejection, with no follow-up exploitation.
5. Uses conservative version parsing for vendor suffixes and prereleases.
6. Caps captured response data at 256 KiB. A truncated response can hide an indicator and must not be interpreted as proof of a patch.
7. Labels PHP memory errors and generic server failures ambiguous. It does not declare either CVE confirmed from those signals.
8. Runs under an outer stage deadline, followed by a separate ordinary recovery request.

This is an attributed adaptation of the scanning method, not an exact replacement for every Nuclei engine behavior. The golden probe length/checksum test vectors were generated by evaluating the original JavaScript builder and compared with the Python port.

## Assetnote provenance

Reviewed commit: `052b56ef4f9bf674aa31ac645068144747bade3d`.

Scanner git blob: `287e97898ab759f6692c698f83d9a30d81db4fbb`.

The included scanner is unchanged and source integrity is checked before execution. Its MIT notice is retained in vendor/ASSETNOTE-LICENSE.txt. Unlike native template mode, it requires the packages in requirements-active.txt. Dependency declarations are minimum versions, not a production dependency lock.

Upstream can retarget detected phpMyAdmin to its diagnostic route on the same origin. Scope authorization must include that behavior. Its HTTP evidence is interpreted conservatively by SIGiL regardless of upstream vulnerable/not-vulnerable labels.

## Workflow and request budgets

Scope validation -> optional signed-evidence validation -> passive assessment of explicit paths -> selected active engine -> recovery request -> optional second active engine -> recovery request -> per-CVE evidence decision -> JSON report.

The CLI validates supplied signed evidence before starting network requests. `timing.total_elapsed_seconds` measures the assessment chain after that validation, not package installation or process startup.

| Selected mode, one endpoint | Methods enabled without trusted evidence | Maximum normal HTTP requests including baseline/recovery | Approximate crafted-body budget |
| --- | --- | --- | --- |
| Passive | 1 | 1 GET | None |
| Native template | 2 | 1 GET + 4 POST + 1 recovery GET = 6 | Up to 29 MiB plus control |
| Assetnote | 2 | Up to 7, including possible phpMyAdmin retarget control | About 29 MiB plus controls |
| Both | 3 | Up to 12 | About 58 MiB plus controls |

Trusted evidence adds one evidence-assessment method and no HTTP requests. More selected paths add baseline GETs; more approved active endpoints repeat the active budgets. Early stopping reduces traffic. These budgets exclude connection-level retries performed by the OS and are not a guarantee of backend work or availability.

Native and Assetnote active stages each have an outer subprocess deadline of `6 * timeout + 10` seconds. At default timeout 5 this is 40 seconds per engine, per selected endpoint. Passive and recovery requests use socket timeouts, not a strict total deadline; configure a whole-job deadline in SIGiL. Timings depend on network latency, response size, worker behavior and early stopping. No fixed completion time is promised.

The report records elapsed seconds for baseline stages, active stages, recovery stages and the chain total. Use those observed measurements rather than a guessed scan duration.

## Interpretation

Matching two related active engines must not increase a result to confirmed RCE. Empty 500s, OOM messages and gateway failures are possible on patched or unrelated systems. No signal, rejected probes, hidden versions or transport failures do not establish a patch. High-confidence runtime conclusions require a correctly implemented trusted collector, vendor advisory mapping and active-worker coverage. Every result continues to set rce_confirmed to false.

## rc5 transport adaptation

`assetnote_adapter.py` imports the hash-pinned, unchanged upstream module in its
isolated subprocess and replaces its HTTP sending function with the same staged
single-attempt transport used by the template method. It invokes `check_url` for
the exact operator-supplied URL, gates controls on HTTP 2xx, limits response capture
to 256 KiB plus one sentinel byte, caps sends at four and blocks route changes.
The upstream payload builder and behavioral classifier remain attributed to the
pinned source. Redirects, non-2xx responses and transport/capture failures stop the
adapter with inconclusive validation. This conservative transport can observe write
timeouts when a server stops reading an upload; that outcome does not establish a
crash. Automatic phpMyAdmin discovery and redirect traversal are disabled.
